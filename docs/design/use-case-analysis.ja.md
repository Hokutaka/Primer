# 設計判断のための利用シナリオ

[English](use-case-analysis.en.md)

**状態: Draft**

この文書は、将来考えられる利用シナリオからPrimerの設計案を評価します。シナリオを製品計画や対応範囲として確定するものではありません。

Primerの使い方を一つに絞るのではなく、具体的な用途を設計のストレステストとして使います。ある設計を採用した場合に、何を観測でき、何を観測できず、どの用途が可能になり、どのコストや危険が生じるかを確認します。

全体の進化方針は[コンパイラ進化計画](evolution-plan.ja.md)、現在の観測境界は[可観測性の契約](observability.ja.md)で定めます。

## 汎用プログラミング言語としての前提

Primerは、あらかじめ選んだ用途だけを扱うための言語ではありません。数値計算、ML、システム処理、可視化、ツール、業務処理などは、許可された用途の一覧ではなく、汎用言語へ持ち込める計算の例です。

したがって、設計では次を原則とします。

- 言語の基本機能を特定用途の名前や実装へ依存させない
- ユーザー定義の型、関数、演算にも、組み込み要素と同じ出自追跡の原則を適用する
- 新しい用途を追加するたびに観測基盤を作り直さない
- 領域固有の高度な最適化を導入する場合も、明示的な変換境界として扱う
- 利用シナリオを、用途を除外する条件ではなく、設計の能力と限界を発見する材料として使う

「何でもできる」ことには、少なくとも次の段階があります。

| 段階 | 意味 |
| --- | --- |
| 表現可能性 | 言語の型、関数、制御構文、データ構造を組み合わせて計算を記述できる |
| 実用性 | 必要なlibrary、runtime、I/O、性能、開発支援がある |
| 出力経路の対応 | 選択したbackendとtargetで実行可能な成果物を生成できる |

Primerの設計は表現可能性を不必要に狭めません。一方、現在の実装がすべてのlibrary、runtime、backendへ同時に対応していることまでは意味しません。言語として可能であることと、現時点で実用的に提供されていることを区別します。

### 計算と表現を分ける

ある計算を表現するために、その領域専用の構文や組み込み型が必須とは限りません。例えば、行列積や畳み込みは、一般的な数値、配列、関数、loop、メモリ操作を組み合わせても記述できます。tensor型、library演算、intrinsic、専用IRは、同じ計算へ異なる構造と意味情報を与える代替表現です。

```text
user-defined abstraction
      ↓
generic functions, loops, and data structures
      ↓
control flow and memory operations
      ↓
backend operations or intrinsics
      ↓
target instructions
```

Primerは一つの表現を唯一の正解として固定しません。代わりに、次を観測できることを重視します。

- 同じ計算がどの表現を通ったか
- 各表現がどの構造と意味情報を保持しているか
- どの変換で高水準の抽象化が失われたか
- 別表現へ置き換えた根拠は何か
- 置き換えによって、どの性質が維持され、どの性質が変化し得るか

専用表現には、意図を保持しやすい、検証規則を持てる、最適化候補を見つけやすいという利点があります。ただし、専用表現がないことを計算不能とみなしません。一般表現で記述された計算から特定の構造を認識できる場合は、認識に使った条件と変換を記録します。認識できない場合も、一般的な要素と変換の観測は維持します。

### 代替表現の同値性

別の表現へ変換できることと、その変換があらゆる意味で同じ結果を保つことは別です。Primerは変換が主張する同値性を区別する必要があります。

| 同値性 | 保持するもの | 例 |
| --- | --- | --- |
| 言語意味上の同値 | Primerが定義する観測可能な振る舞い | 整数演算を意味が同じ命令列へloweringする |
| bit単位の同値 | 出力値のbit patternと例外的挙動 | 浮動小数点の演算順序も維持する変換 |
| 数値的な許容範囲内 | 定義した誤差または許容差 | 近似演算、mixed precision、quantization |
| 利用者が定義した契約上の同値 | shape、範囲、統計的性質など指定した条件 | MLまたは科学技術計算向けの近似変換 |
| 同値性を未確認 | 同じ目的に見えても保証を持たない | 根拠なく検出したpatternへの置き換え |

例えば、実数の数学では同じ式でも、浮動小数点の`(a + b) + c`と`a + (b + c)`は丸めによって異なる値になる場合があります。演算融合、並べ替え、vector化、quantizationなどを「代替表現」として採用するときは、何を維持する変換かを明示します。

出自は二つの表現の関係を示せますが、同値性そのものの証明にはなりません。変換規則、適用条件、型規則、検証、テスト、必要に応じた数値比較を組み合わせます。

### 一般的な観測と領域固有の説明

任意のユーザー定義プログラムに対して、Primerは次のような一般的な情報を観測できます。

- 型と名前がどう解決されたか
- どの関数、値、式がどのIR要素へ変換されたか
- 一つの要素がどのように分解、統合、消去されたか
- backendとtargetがどの表現を選んだか

しかし、任意のコードを見ただけで、その領域上の意図まで安全に推測できるとは限りません。例えば、loop、配列アクセス、乗算、加算を組み合わせた関数を実行でき、変換を追跡できても、それが「畳み込み」「行列積」「信号filter」のどれを意図したものかは自動的に断定できません。

領域固有の説明には、次のような明示的な意味情報が必要になる場合があります。

- 標準libraryまたは利用libraryの既知の演算
- 型、trait、interface、contract
- ソース上の明示的なannotation
- 名前と責務を持つ領域固有のloweringまたは最適化pass

どの方法を採用するかは将来の設計事項です。重要なのは、領域上の意図を根拠なく推測しないことと、明示された意味がloweringで失われる場合にその変換を追跡することです。

この区別から、観測モデルには次が求められます。

- ユーザー定義要素にも識別子と出自を付けられる
- 抽象化の名前と境界を、観測に有用な段階まで保持できる
- inlining、fusion、specializationなどで抽象化が失われた地点を記録できる
- 任意の自由文だけに依存せず、明示的な意味情報を型付きで関連付けられる余地がある
- 領域固有情報がなくても、一般的なコンパイラ変換の説明は維持できる

## シナリオの評価方法

各利用シナリオは、次の観点で評価します。

| 観点 | 確認すること |
| --- | --- |
| 観測したい対象 | 値、型、IR要素、変換、成果物、実行状態など何を見るか |
| 答えたい問い | その観測によって何を説明したいか |
| 必要な能力 | 出自、変換記録、選択理由、Emission Map、実行時収集など何が必要か |
| 観測できないこと | その能力だけでは何を判断できないか |
| 観測方法 | コンパイル時、実行時、静的解析、外部測定のどれで収集するか |
| 観測による影響 | 成果物、実行順、メモリ使用量、性能が変化しないか |
| セキュリティ | ソース、入力、秘密情報、モデル、利用者データを含まないか |
| 再現性 | 同じ条件で比較できるか、乱数や並列実行をどう扱うか |
| 公開境界 | 内部情報、公開スキーマ、外部ツールのどこに置くか |
| 実装コスト | 保存量、実行負荷、バックエンド対応、互換性負担はどの程度か |

利用シナリオは、特定機能の採用を正当化するためだけに使いません。設計案が説明できないものと、用途に対して過剰な仕組みも明らかにします。

## シナリオ1: 数値計算とML

Primerは汎用言語としてMLの計算も一般的な言語機能の組み合わせで表現できる方向を目指します。現在の実装には、そのための関数、制御構文、データ構造、library、runtimeなどがまだ揃っていません。tensor型や専用演算は表現可能性の必須条件ではなく、実用性や最適化のために選べる表現です。このシナリオはMLを特別に許可された用途とするものではなく、数値計算を持ち込んだときにPrimerの可観測性がどのような価値を持つかを検討します。

数値計算では、プログラムが最終的に値を出したことだけでなく、その値がどの型、精度、変換、対象表現を通って得られたかが重要です。この関係を追跡できることは、Primerにとって大きな利点になります。

### 観測したい層

数値計算とMLの観測対象は、少なくとも四つの層に分けられます。

#### 1. 数値の意味

- ソース上の数値型
- 型推論の結果
- literalの型と表現可能な範囲
- 演算の入力型、結果型、累積型
- shape、次元、要素型などの将来の構造化型情報

この層は、Primerがプログラムをどのような数値計算として解釈したかを表します。

#### 2. 数値変換

- 明示的または暗黙的な型変換
- mixed precisionでの昇格と縮小
- quantizationとdequantization
- 演算の融合と分解
- aggregate、vector、tensorのlayout変更
- backend命令またはkernelの選択

この層は、解決済みの数値的意味を対象表現へどう移したかを表します。

#### 3. 実行時の数値挙動

- 実際に計算された値
- 最小値、最大値、平均、分散などの要約
- `NaN`、正負の無限大、overflow、underflow
- quantizationによる飽和
- gradientの消失または発散
- backend間または実行間の数値差

この層は実際の入力と実行へ依存します。コンパイル結果だけからは得られません。

#### 4. 実行特性

- 実行時間
- コードサイズ
- メモリ使用量
- 転送量
- kernel起動回数
- 対象ハードウェアの利用状況

この層は性能測定です。Primerが変換と選択理由を説明し、Whitebaseや対象runtimeなどの利用側が測定を担当します。

### 答えられると有用な問い

| 問い | 必要な情報 |
| --- | --- |
| なぜこの値は`f32`になったか | 型解決の出自と選択理由 |
| どこで精度が失われたか | 数値型と変換の連鎖、変換前後の値または誤差 |
| この`NaN`はどの演算から発生したか | 実行時値、演算の出自、最初の異常発生位置 |
| なぜ二つのbackendで値が異なるか | 共通の数値的意味、各lowering、同じ入力と実行条件 |
| どの演算が融合されたか | 多対一の出自関係と変換記録 |
| なぜこのkernelまたは命令が選ばれたか | target条件、capability、構造化された選択理由 |
| quantization誤差はどこで増えたか | scale、zero point、変換記録、段階ごとの数値比較 |
| gradientが消失した地点はどこか | 演算グラフの出自と実行時のgradient要約 |
| 変換によって実際に速くなったか | Primerの変換記録と、外部で測定した性能値 |

## 数値を観測する能力の段階

「数値が見える」という表現には、異なる能力が含まれます。どの段階を選ぶかによって、可能な用途とコストが変わります。

### 1. コンパイル時の型と定数だけを観測する

**できること**

- 型推論、literal解決、変換命令を説明する
- mixed precisionの経路を静的に調べる
- backend間の数値型と命令選択を比較する
- 実際の入力値を収集せずに観測する

**できないこと・限界**

- 実行時の`NaN`、overflow、値の分布は分からない
- 入力データに依存する精度低下を検出できない
- 実際の性能は分からない

**主な用途**

- 型設計とloweringの検証
- 精度変換の静的な監査
- backend比較

### 2. 静的な範囲や誤差を解析する

**できること**

- 値が取り得る範囲を保守的に推定する
- overflowや精度低下の可能性を実行前に見つける
- 実入力を保存せずに数値上の危険を調べる

**できないこと・限界**

- 解析結果は保守的になり、実際には起きない問題も含む場合がある
- 複雑な演算やloopでは計算量と精度の両立が難しい
- 実際の値や頻度は分からない

**主な用途**

- 数値安全性の診断
- quantization候補の調査
- 実行前の範囲検証

### 3. 実行時の要約値を収集する

**できること**

- 最小値、最大値、平均、分散、`NaN`件数などを調べる
- tensor全体を保存せずに分布の変化を比較する
- 異常が最初に現れた演算を絞り込む

**できないこと・限界**

- 要約から個別の異常値や配置を復元できない
- 平均値が局所的な問題を隠す場合がある
- 収集処理が実行時間やメモリ使用量へ影響する
- 要約値から元データの性質が推測される場合がある

**主な用途**

- `NaN`、overflow、gradient異常の調査
- quantization校正
- モデル層ごとの数値分布比較

### 4. 実行時の値をサンプリングする

**できること**

- データ量を制限しながら具体的な値を確認する
- 特定位置、特定演算、特定条件の値を追跡する
- backend間の数値差を具体例で比較する

**できないこと・限界**

- サンプリングされなかった異常を見逃す
- サンプリング方法によって観測結果が変わる
- 再現可能なサンプリング規則が必要になる
- 個別データを取得するため機密性が高い

**主な用途**

- 数値差分の原因調査
- 小規模なモデルまたは入力のデバッグ
- 要約値で見つけた異常の詳細確認

### 5. 実行時の完全な値を収集する

**できること**

- 要素単位の完全な比較と再解析を行う
- 特定実行について、値の伝播を詳細に追跡する
- 後から別の要約方法を適用する

**できないこと・限界**

- 大きなtensorや長い実行では保存量が現実的でない
- モデル重み、学習データ、利用者入力をそのまま含む可能性がある
- 収集による実行への影響が大きい
- 並列実行や外部deviceの正確な再現を保証しない

**主な用途**

- 小さく限定した再現ケース
- 数値実装の詳細検証
- 厳密なbackend差分調査

完全な値の収集を通常の観測方法にはしません。明示的に対象と上限を指定した調査機能としてのみ検討します。

## MLシナリオから得られる設計上の示唆

このシナリオを採用予定に含めなくても、現在の設計が次を不必要に妨げないか確認できます。

### 数値の意味を早期に失わない

- 型、精度、変換の有無をPrimer IRで明示する
- backendが型推論や数値変換を暗黙に繰り返さない
- 将来のshapeや要素型を、文字列だけでなく型付き情報として保持できる余地を残す

これは現在の「型をbackend lowering前に解決する」という方針と一致します。

### 一つの`Span`を出自モデルの上限にしない

演算融合では複数のソース演算が一つのbackend要素になり、分解では一つの演算が複数要素になります。一対多と多対一を扱える出自が必要です。

### 観測データをscalarとテキストだけに限定しない

将来の観測対象は、shape、layout、範囲、統計量、複数の値を持つ可能性があります。公開形式を早く固定せず、内部では型付きでサイズ制限可能なデータとして扱う案が適しています。

### 選択理由を構造化する

`used f32 because it is faster`のような自由文だけでは比較できません。少なくとも理由の種類、適用条件、対象要素を構造化し、人間向け文面は交換可能にします。

### コンパイル観測と実行時instrumentationを分ける

型、IR、lowering、成果物の観測は、成果物を変更しない受動的な観測として扱えます。一方、実行時値を取得するには、VMまたは生成コードへinstrumentation（計測処理）を追加する場合があります。

instrumentationを利用する実行は、通常実行とは別の明示的なモードとして扱います。

- instrumented artifactであることを記録する
- instrumentation設定を実験条件へ含める
- 通常成果物と同じ性能だとみなさない
- 意味上の出力が変わっていないことを検証する
- 収集先と上限を明示する

### コンパイルの再現性と実行の再現性を分ける

同じPrimer入力から決定的な成果物が生成されても、乱数、並列実行、GPU、外部library、入力順によって実行時値が変わる場合があります。

```text
compile reproducibility  同じ明示的なコンパイル条件から同じ観測結果と成果物を得る
run reproducibility      同じ実行条件と入力から比較可能な実行結果を得る
```

Primerは前者を担当します。後者に必要なseed、device、runtime、library、入力識別は、実行を担当する側が記録します。

## セキュリティとプライバシー

秘密の値を型として扱う設計は、[Secret値の設計](secrets.ja.md)で整理します。

実行時の数値は、ソース本文やファイルパスとは別の機密情報です。

- 学習データ
- 利用者入力
- モデルの重み
- label
- 埋め込み表現
- gradient
- 統計量から推測できるデータの特徴

したがって、ソース開示を許可したことを実行時値の収集許可として扱いません。権限と設定を分けます。

実行時観測を導入する場合は、少なくとも次を守ります。

- 初期状態では収集しない
- 対象となる値、演算、段階を明示する
- 要素数、byte数、実行時間に上限を設ける
- 要約、サンプリング、完全収集を区別する
- terminalへ巨大な値や制御文字を直接出力しない
- 永続化と外部送信を別の許可として扱う
- 観測識別子から実行や値の変更を行えるようにしない

## 観測による実行への影響

実行時値の収集は、次を変える可能性があります。

- 命令スケジュール
- 演算融合
- メモリ配置と使用量
- device間転送
- 並列実行のタイミング
- 実行時間

そのため、instrumentationを加えた実行の性能を通常実行の性能として報告しません。

必要に応じて、次の観測方法を区別します。

| 方法 | 成果物への影響 | 得られる情報 |
| --- | --- | --- |
| コンパイル時の受動的観測 | 変更しない | 型、IR、変換、選択理由、成果物対応 |
| Primer VM内部の観測 | VM実行経路に負荷を加える | bytecode単位の値と実行状態 |
| instrumented artifact | 成果物を明示的に変更する | 対象runtimeでの値とevent |
| 外部profilerまたはruntime | Primerの外側 | device、kernel、性能、外部実行状態 |

観測結果には、どの方法で取得したかを必ず含めます。

## Primerと外部ツールの境界

数値計算とMLのシナリオでも、Primerがすべてを担当する必要はありません。

### Primerが担当する候補

- 数値型と数値的意味の解決
- Primer内部で行った変換と出自
- instruction、kernel、layoutなどを選んだ理由
- Primer VMで明示的に有効化した値の観測
- Primerが生成した成果物までのEmission Map

### 利用側が担当する候補

- dataset、model、入力の管理
- 外部ML runtimeの実行
- deviceとlibraryの選択
- 性能測定
- 外部compiler、driver、kernel内部の観測
- 実験結果の保存と比較

Primerが外部ツールの情報を受け取って関連付けることと、Primer自身がその変換を行ったと主張することは区別します。

## このシナリオで実装順を固定しないもの

次の機能は、PrimerでMLを実用的または効率的に扱うための表現や実装戦略になり得ます。ただし、計算を表現するための必須条件とはみなしません。また、このシナリオだけで組み込み機能、library、外部runtimeのどこに置くかや、実装順を固定しません。

- tensor型
- 自動微分
- GPU backend
- ML graph IR
- kernel compiler
- runtime instrumentation
- model形式

これらを追加する場合は、それぞれ独立した設計判断が必要です。このシナリオから今決めるのは、汎用言語として数値計算を表現できることと、将来の数値的な説明可能性を不必要に閉じないための境界です。

## 設計案を評価する質問

新しいIR、型、観測API、backend機能を設計するときは、このシナリオに対して次を確認します。

1. 数値型と精度の決定を追跡できるか
2. 一対多と多対一の数値変換を表せるか
3. 変換内容と選択理由を分けて保持できるか
4. scalar以外の型付き観測データを将来表せるか
5. 観測量へ上限を設定できるか
6. ソース、実行時値、外部送信の許可を分離できるか
7. instrumentationが通常成果物と実行へ与える影響を識別できるか
8. Primerの変換と外部runtimeの変換を区別できるか
9. コンパイルの再現性と実行の再現性を区別できるか
10. その能力を追加しない場合、どの用途が不可能になるか
11. 一つの計算を複数の代替表現として追跡できるか
12. 表現を置き換える変換が、どの同値性を保証するか示せるか

すべてへ今すぐ対応する必要はありません。設計によって将来の選択肢が閉じる場合に、その影響を理解して判断できることが目的です。

## 今後追加できるシナリオ

同じ形式で、次のような利用シナリオを追加できます。

- 科学技術計算における誤差と再現性
- 最適化passの教育と可視化
- 複数backendとtargetの比較
- agentによるコンパイラ調査
- セキュリティ監査と機密情報を開示しない観測
- 組み込み環境でのコードサイズと資源利用の説明

シナリオを増やす場合も、Primerの用途を一つへ固定するのではなく、設計案が異なる要求へどの程度耐えられるかを調べます。
