# コンパイラ進化計画

[English](evolution-plan.en.md)

**状態: Draft**

この文書は、Primerを今後拡張するための課題、必要な能力、設計案、判断事項、実装順を整理します。現在の言語仕様や公開互換性を変更する決定書ではありません。合意した内容は、[コンパイラ設計](architecture.ja.md)、[可観測性の契約](observability.ja.md)、[言語リファレンス](../reference/language.ja.md)へ反映します。

具体的な将来用途から設計案の可能性と限界を評価する方法は、[設計判断のための利用シナリオ](use-case-analysis.ja.md)で整理します。

## 読み方

最初の検討では、次の章を順に読むことを想定しています。

1. 「目的」でPrimerの判断基準を確認する
2. 「観測によって答えたい問い」と「Primer固有の設計課題」で不足している問いを探す
3. 「設計選択が可能性に与える影響」で案の利点と制約を比較する
4. 「Issue #2で決めること」で直近の判断事項を確認する

「能力、限界、用途」は、個別の観測能力が必要になったときの参照資料です。「実装上の課題」以降は、設計判断をIssueと実装順へ落とすために使います。

現在の主要な検討点は、説明に出自だけでなく変換と選択理由を含めるか、Structured Primer IRとControl-flow IRを分けるか、バックエンド対応をどのように進めるかの三点です。

## 目的

Primerは、コンパイラによる変換を観測可能にするための実験用プログラミング言語です。言語機能を小さく保つことや、実装を単純に保つこと自体を目的にはしません。高度な解析、lowering、最適化を導入する場合も、その境界、入力、結果、理由を追跡できる状態を保ちます。

Primerは汎用プログラミング言語として、用途を特定の領域へ限定しません。利用シナリオは対応する用途を選別するものではなく、どのような計算を持ち込まれても設計が不必要に選択肢を閉じないかを検査するために使います。

汎用性の必要条件として、利用者が値へ意味のある名前と構造を与えるユーザー定義型を設計します。特定領域の型をすべて組み込みにするのではなく、利用者が一般的な型、関数、データ構造から必要な表現を作れることを目指します。

広い可観測性を安全に利用するため、秘密の値を観測と通常の外部出力から守る`Secret`を設計します。`Secret`はpassword専用ではなく、任意のユーザー定義型を含む値へ適用できる安全境界とします。詳細は[Secret値の設計](secrets.ja.md)で検討します。

Primerは速さの追求を避けるのではなく、どの変換が速さに寄与したかを説明可能にします。その結果として、観測結果に基づいて速さを追求できることを目指します。

観測可能であることと、外部からコンパイル処理へ干渉できることは別です。観測データは読み取り専用とし、コンパイラ内部を書き換える権限として扱いません。

## 現在地

現在のPrimerには、次の基礎があります。

- 型付きでバックエンドに依存しないPrimer IR
- Primer IRから各バックエンドIRへの明示的なlowering
- Primer IRと生成成果物という二つの公開観測境界
- AST、Primer IR、診断で利用するUTF-8バイト範囲の`Span`
- bytecode命令の`Source(span)`と`Synthetic`による出自
- bytecode命令番号とソース位置を関連付けたVM実行診断
- 決定的なテキスト出力を検証するスナップショットテスト
- 観測と制御、ソース開示、再現性に関する設計上の境界

現在の処理経路は、主に直線的な文と式を対象としています。

```text
Source
  -> Tokens
  -> AST
  -> typed Primer IR
  -> Backend IR
  -> Artifact
```

関数、制御構文、aggregate type、最適化が加わると、要素同士の関係は一対一ではなくなります。そのため、現在の`Span`だけを引き回す方法では、Primerが目的とする説明可能性を維持できません。

## 観測によって答えたい問い

今後の観測モデルは、少なくとも次の問いに答えられる必要があります。

| 方向 | 問い |
| --- | --- |
| ソースから前方 | このソース要素は、各段階で何へ変換されたか |
| 成果物から後方 | このIR要素または生成命令は、どのソース要素に由来するか |
| 段階間 | どのpassまたはloweringが、この要素を生成、変更、統合、分解したか |
| コンパイラ生成 | ソースに存在しない補助要素は、なぜ必要になったか |
| 消去 | 以前の段階に存在した要素が、なぜ後の段階に存在しないか |
| 診断 | 問題がどの段階と要素で発生し、ソースのどこへ対応するか |
| 比較 | 同じ入力に対する異なる経路、ターゲット、オプションの結果は何が違うか |

この問いの一覧は、特定のファイル形式やCLIコマンドを要求するものではありません。まず内部で答えられる情報を保持し、その後で公開方法を決めます。

## Primer固有の設計課題

一般的なコンパイラ設計では、型検査やコード生成を正しく実装できることが中心になります。Primerではそれに加えて、設計を変更するたびに次を確認します。

- その変更によって、何を新しく観測できるか
- その設計では、何を観測できないまま残すか
- 観測結果から、どのような調査、比較、説明が可能になるか
- 情報を保持するために、どの程度の実装コストとデータ量が必要か
- 観測機能が成果物、セキュリティ、再現性へ影響しないか

### 説明を構成する情報を分ける

Primerが変換を説明するために扱う情報は、次の五つに分けられます。

| 情報 | 答える問い | 例 |
| --- | --- | --- |
| Provenance / 出自 | どこから来たか | この命令はソースの式とIR要素に由来する |
| Transformation / 変換 | 何が起きたか | 一つの式が三つの命令へ分解された |
| Rationale / 選択理由 | なぜ行ったか | 対象ABIが引数の拡張を要求するため |
| Observation / 観測表現 | どのように見せるか | pass前後のスナップショットと対応表 |
| Measurement / 測定 | 結果として何が起きたか | 実行時間、コードサイズ、命令数が変化した |

これらは互いに代用できません。

- `Span`だけでは、変換内容や選択理由は分かりません。
- pass名だけでは、どの要素がどう変わったかは分かりません。
- 選択理由を記録しても、その変換が実際に高速だったことは証明できません。
- 測定値だけでは、どの変換が差に寄与したかを説明できません。

Primerは出自、変換、選択理由を担当します。実際の外部ツールチェーンでの性能測定はWhitebaseなどの利用側が担当し、Primerの観測結果と組み合わせます。

### 情報が失われる地点を境界として扱う

新しいIR段階や観測点は、実装モジュールの都合だけで決めません。次の変換で前段の意味構造を後から復元できなくなる場合、その地点は明示的な変換境界の候補です。

例を示します。

- structured `if`をbasic blockとbranchへ変換する
- aggregateをアドレス計算と個別のメモリ操作へ分解する
- 抽象的な関数呼び出しを特定ABIの引数操作へ変換する
- 最適化によって式、分岐、ロードを統合または消去する

変換後の結果だけで十分に説明できない場合、変換前後の表現または変換記録を保持します。

### 起きなかった変換をどこまで扱うか

実験では「なぜ変換したか」だけでなく、「なぜ候補だった変換を適用しなかったか」も重要になる場合があります。

すべての候補と不適用理由を常に記録すると、観測量と実装コストが大きくなります。次の段階を選択肢とします。

1. 適用された変換だけを記録する
2. 明示的に選択したpassについて、不適用理由も記録する
3. 詳細な調査モードで、検討した候補を限定的に記録する

初期状態では1を基本とし、具体的な実験用途が生じたpassから2または3を追加する案を第一候補とします。

### 決定的な表示と観測事実を区別する

比較しやすいように観測結果を並べ替えると、実際の処理順が見えなくなる場合があります。Primerは次の二つを混同しません。

```text
canonical order  比較と保存のための決定的な表示順
execution order  実際に処理または選択された順序
```

実際の順序に意味がある場合は、その順序を観測データとして保持します。表示の安定化によって、観測対象だった順序を書き換えません。

### 複数バックエンドの対応関係を扱う

同じPrimer IR要素が、異なる出力経路で異なる数と種類の要素へloweringされます。Primerでは、各成果物を個別に見るだけでなく、共通の意味からどのように分岐したかを比較できることが重要です。

この比較には、次の区別が必要です。

- Primerとして共通の意味
- 出力経路が選んだ表現
- ターゲットやABIが要求した変換
- 外部ツールチェーンがPrimerの外側で行った変換

Primerが説明できるのは、自身が担当した境界までです。外部コンパイラの内部判断をPrimerの判断として記録しません。

## 能力、限界、用途

観測能力は一度に完成させるものではありません。各能力を追加したときに可能になることと、依然として不可能なことを明確にします。

### ソース範囲

**できること**

- 診断を行番号と列番号へ対応させる
- AST、Primer IR、bytecode命令をソース範囲へ戻す
- エディタで対応箇所を選択表示する

**できないこと・限界**

- 同じ範囲から生成された複数要素を区別できない
- 複数要素の統合、消去、選択理由を表せない
- 複数ソースファイルでは、`Span`だけではファイルを識別できない

**用途**

- 診断表示
- ソースと単一のIR要素の強調表示
- 現在のbytecode実行エラーの逆引き

### コンパイル内の要素識別子

**できること**

- 同じ`Span`を共有する要素を区別する
- 段階内と段階間の関係を正確に参照する
- 一つの要素から生成された複数要素を列挙する

**できないこと・限界**

- 識別子だけではソース位置、変換内容、選択理由は分からない
- コンパイルをまたぐ安定性を別に定義しない限り、過去結果との直接対応には使えない
- 識別子を付けるだけでは、消去された要素の理由は残らない

**用途**

- UI上での要素選択と追跡
- 出自グラフと対応表
- 構造化された観測データ内の参照

### 一対多・多対一の出自関係

**できること**

- 式から複数命令への分解を追跡する
- 複数の値や分岐から一つの結果への統合を追跡する
- ソース、Structured IR、Control-flow IR、Backend IRの間をたどる

**できないこと・限界**

- 関係だけでは、変換規則や選択理由は分からない
- 消去されて後段に対応要素を持たない要素は、別の記録が必要になる
- 関係を無制限に保持すると、データ量が大きくなる

**用途**

- ソースから生成命令までの前方追跡
- 成果物からソースまでの逆引き
- バックエンド間でのlowering結果の比較

### 段階ごとの不変なスナップショット

**できること**

- 変換前後を直接比較する
- コンパイラの可変内部状態を渡さずに観測する
- 回帰テストで変換結果を固定する
- エージェントや外部ツールへ、境界が明確な入力を渡す

**できないこと・限界**

- スナップショットだけでは、差が生じた理由は分からない
- 中間の操作を保存しなければ、複数の変換を一つずつ再現できない
- 大きなプログラムですべての段階を保存すると、時間と容量を消費する

**用途**

- pass前後のdiff
- コンパイラ回帰の調査
- Tint*による段階別表示
- エージェントによる構造化解析

### 変換記録

**できること**

- 生成、置換、統合、分解、消去を操作として説明する
- スナップショット間の差がどのpassで生じたかを特定する
- 消えた要素を後段の結果とは別に記録する

**できないこと・限界**

- 記録した操作が意味を保存していることを自動的には証明しない
- 低水準の操作をすべて記録すると、説明が機械的で読みにくくなる
- pass実装と記録内容が一致するよう維持する必要がある

**用途**

- 最適化の説明
- 予期しないコード生成差分の原因調査
- コンパイラ教育と変換の可視化

### 選択理由

**できること**

- 命令、ABI操作、最適化を選んだ規則を説明する
- 同じ意味がターゲットごとに異なる表現になる理由を説明する
- 選択条件の変更による回帰を見つける

**できないこと・限界**

- 選択理由は、実際の性能向上を証明しない
- 自由文だけでは比較や機械処理が難しい
- 理由の分類を細かくしすぎると、内部実装を公開契約として固定しやすい

**用途**

- 命令選択とABI loweringの説明
- 最適化判断の調査
- Primerの観測結果とWhitebaseの測定結果の関連付け

選択理由は、安定した種類と必要に応じた説明文を分けて保持する案を第一候補とします。

### 不適用理由

**できること**

- 期待した最適化が行われなかった理由を調査する
- 最適化条件やターゲット機能の違いを比較する
- passの改善候補を見つける

**できないこと・限界**

- すべての候補を記録すると、観測量が急増する
- 候補を列挙しない実装では、完全な不適用理由を作れない
- 通常のコンパイルで常に必要な情報ではない

**用途**

- 最適化開発
- ターゲット別の性能差の調査
- 特定passの詳細な実験

### Emission Map

**できること**

- 生成テキストの範囲からBackend IRとソースを逆引きする
- 成果物を変更せずに対応箇所を強調表示する
- 同じPrimer IR要素が各バックエンドで何になったか比較する

**できないこと・限界**

- Primerの外で外部コンパイラが行った変換までは追跡できない
- emitterが出力範囲を正確に記録する必要がある
- 出力後に別ツールが整形すると、範囲の対応が失われる

**用途**

- Tint*でのソースと成果物の連動表示
- 生成コードの調査
- バックエンド差分の比較

### バックエンドのcapability情報

**できること**

- 言語機能を対応可能な出力経路から段階的に導入する
- 未対応機能を実行前に診断する
- ツールが利用可能な経路を機械的に選別する

**できないこと・限界**

- 対応を表明するだけでは、バックエンド間の意味の一致を証明しない
- 対応状況が細かすぎると、組み合わせ管理が複雑になる
- 全経路で同時に利用できるという単純な契約は失われる

**用途**

- 新機能の段階的な実装
- 実験用バックエンドの追加
- CLI、Tint*、Whitebaseでの事前検証

### バージョン化された公開観測スキーマ

**できること**

- Tint*、Whitebase、エージェントが構造化された観測結果を安定して利用する
- 異なるPrimerバージョンの結果を識別する
- テキスト表示を解析せずに、要素と関係を調べる

**できないこと・限界**

- 公開後は互換性の維持と移行が必要になる
- 内部IRをそのまま公開すると、実装実験の自由を失う
- スキーマが存在しても、必要な出自や理由を内部で保持していなければ説明できない

**用途**

- 長期間保存する実験結果
- IDEと可視化ツール
- 読み取り専用のエージェント解析
- 複数バージョン間の比較

## 設計選択が可能性に与える影響

| 設計選択 | 可能になること | 難しくなること・失うもの |
| --- | --- | --- |
| Structured IRとControl-flow IRを分ける | 構造がCFGへ変わる境界を観測でき、バックエンド間で制御フローを共有できる | IR段階、検証、出自関係が一つ増える |
| Structured IRから各バックエンドへ直接loweringする | パイプラインと実装段階を少なくできる | 制御フロー変換が各バックエンドへ分散し、共通比較が難しくなる |
| すべてのバックエンドを同時対応する | 全出力経路で言語仕様が常に一致する | 一つの機能変更が大きくなり、意味とIRだけを先に検証しにくい |
| capabilityを明示して段階導入する | 小さな縦方向の実装と実験ができる | 未対応診断、対応表、ツール側の分岐が必要になる |
| 観測情報を成果物へ埋め込む | 単一ファイルだけで対応を調べられる | 成果物が変化し、後続ツールや性能へ影響する可能性がある |
| Emission Mapを副次データにする | 成果物を変えずに逆引きできる | 成果物と対応表を組として管理する必要がある |
| スナップショットだけを保持する | 実装と比較が比較的単純になる | 変換理由と消去過程を直接説明できない |
| 変換記録も保持する | 生成、変更、消去を説明できる | 記録量、実装負担、表示方法の設計が増える |
| 内部モデルを早期に公開スキーマ化する | 外部ツールを早く構築できる | 内部設計の変更が互換性問題になる |
| 内部利用で検証してから公開する | 用途に基づいてスキーマを絞り込める | 外部ツールから利用できる時期が遅くなる |

## 想定用途

### 対話的なコンパイラ観察

利用者がソース式を選択し、Structured IR、Control-flow IR、Backend IR、成果物で対応する要素を確認します。逆に、生成命令からソースと変換理由をたどります。

必要な能力は、ソース範囲、要素識別子、段階間の出自関係、Emission Mapです。

### コンパイラ回帰の調査

同じ入力に対する二つのPrimerバージョンのスナップショットを比較し、最初に差が生じたpassと要素を特定します。

必要な能力は、決定的なスナップショット、pass識別、変換記録です。

### 最適化実験

Primerで適用した変換と選択理由を確認し、Whitebaseで実行時間やコードサイズを測定します。変換の説明と実測結果を分離したまま関連付けます。

必要な能力は、変換記録、選択理由、明示的なコンパイル条件、外部測定との実験識別です。

### バックエンド比較

同じPrimer IR要素がC、LLVM IR、QBE IR、WAT、アセンブリ、bytecodeでどのように表現されたかを比較します。

必要な能力は、共通の意味要素、各loweringの出自、Emission Map、ターゲット条件です。

### エージェントによる解析

エージェントへ、必要な段階だけを含むサイズ制限付きの構造化スナップショットを渡します。エージェントは関係を読み取れますが、識別子を使ってコンパイラ状態を変更することはできません。

必要な能力は、バージョン化された読み取り専用スキーマ、サイズ上限、明示的なソース開示です。

### 診断の説明

エラー位置だけでなく、どの段階のどの規則が問題を検出し、どの前段要素に関係するかを示します。

必要な能力は、構造化診断、段階識別、出自関係、安全な描画です。

## 説明できることと証明できないこと

Primerの観測結果が示せる範囲を過大に主張しません。

- 出自関係は、変換が意味を保存していることの証明ではありません。
- 選択理由は、実際に性能が向上したことの証明ではありません。
- 決定的な成果物は、異なるターゲットで同じ実行結果になることの証明ではありません。
- capability情報は、バックエンド実装が正しいことの証明ではありません。
- Emission Mapは、外部ツールチェーン内の変換まで追跡するものではありません。
- スナップショットだけでは、消去された要素の理由を完全には説明できません。

正しさは検証とテスト、性能は測定、外部変換は外部ツールの記録と組み合わせて判断します。

## 設計Issueの判断テンプレート

今後の設計Issueでは、機能名と実装案だけでなく、次の項目を記載します。

1. 解決したい問題
2. 観測によって答えたい問い
3. 現在保持している情報
4. 追加が必要な情報と変換境界
5. 候補となる設計
6. 各候補で可能になること
7. 各候補で不可能または困難になること
8. 想定用途
9. セキュリティと外部干渉への影響
10. 再現性と決定性への影響
11. 公開互換性への影響
12. 検証方法と完了条件

この形式により、「実装できるか」だけでなく、「Primerとして何を説明できる設計か」を判断します。

## 実装上の課題

### `Span`は位置であり、要素の同一性ではない

`Span`はソース位置を示せますが、同じ範囲から生成された複数の要素を区別できません。また、複数の範囲から生成された一つの要素や、ソースに直接対応しない要素も十分に表せません。

位置情報と、コンパイル中の要素を識別する情報を分ける必要があります。

### 変換は一対一とは限らない

将来は次の関係が発生します。

- 一つの式を複数命令へ分解する
- 複数の値や分岐を一つの値へ合流させる
- aggregateを複数のロード、ストア、アドレス計算へloweringする
- 最適化によって要素を統合または消去する
- ABIやターゲットの都合で補助命令を生成する

各要素に一つの`Span`を付けるだけでは、これらの関係を説明できません。

### 構造化された意味と制御フローは役割が異なる

現在のPrimer IRは、解決済みのPrimerの意味をソースに近い構造で表します。実装済みの`if`も構造化された文として保持し、各バックエンドIRでbranchと合流点へloweringします。将来、関数、loop、early returnが加わると、basic block、branch、terminatorを共通に表す制御フロー段階が必要になる可能性があります。

Primer IRを直接CFGへ変えると、ソースに近い意味構造が早い段階で失われます。反対に、構造化IRだけにすべての役割を持たせると、バックエンドごとに制御フローの解釈を繰り返すことになります。

### 生成成果物の位置とソースの対応がない

現在は、生成されたbytecode命令からソース位置を求められます。しかし、C、LLVM IR、QBE IR、WAT、アセンブリのテキスト上の範囲と、内部要素やソース要素の対応は保持していません。

生成成果物へコメントや識別子を埋め込むと、成果物自体を変えてしまいます。対応情報は成果物から分離して保持する必要があります。

### バックエンドの対応方針が未定義

言語機能を追加するたびに、現在のすべての出力経路を同時に対応させるか、対応状況を明示しながら段階的に導入するかを決める必要があります。

段階的に導入する場合は、未対応機能をpanicや不正な出力ではなく、構造化された診断として報告できなければなりません。

## 必要な能力

### 今後の言語拡張より前に必要なもの

- 制御フローを表す新しい内部段階を導入するかどうかの決定
- 一対多、多対一、コンパイラ生成を扱える出自の概念モデル
- 新しい言語機能に対するバックエンド対応方針
- 各変換段階が保持すべき不変条件

### 最初の制御構文で導入済みのもの

- blockとlexical scope
- compilation-localな束縛ID
- 構造化された`if`を保持するPrimer IR
- Bytecodeと各バックエンドIRにおけるbranchと決定的な合流点
- 条件型とスコープ違反を報告する診断

共通の制御フローIR、変換間の出自追跡、分岐後のSSA値を合流させる共通規則は未導入です。現在のQBE loweringは束縛を明示的なスタックスロットへ置き、分岐を越える可変値の意味を保持します。

### 公開観測機能を増やす前に必要なもの

- 内部状態から切り離した読み取り専用スナップショット
- スキーマのバージョン
- 決定的な識別子と並び順
- ソース本文とファイルパスの明示的な開示設定
- secret値を観測スナップショットへ取り込まないcapture時のredaction
- 出力サイズ、深さ、要素数の上限
- 未知のフィールドや新しいpassを扱う互換性方針

## 設計案

### IRを役割ごとの段階へ分ける

次の構成を第一候補とします。

```text
Primer Source
      ↓
AST
      ↓
Typed Structured Primer IR
  - resolved types and names
  - source-level functions and structure
  - backend independent
      ↓
Control-flow Lowering
      ↓
Control-flow IR / Core IR
  - function bodies as basic blocks
  - basic blocks
  - explicit terminators
  - backend independent
      ↓
Backend Lowering
      ↓
Backend IR
      ↓
Emitter
      ↓
Artifact
```

`Control-flow IR`と`Core IR`は仮称です。名称と正確な責務は設計時に決定します。

各段階の役割は次のとおりです。

| 段階 | 主な責務 | 含めないもの |
| --- | --- | --- |
| Structured Primer IR | Primerの型付きの意味と構造 | ABI、レジスタ、対象命令 |
| Control-flow IR | 明示的な関数、block、branch、terminator | ターゲット固有ABI、レジスタ |
| Backend IR | ターゲットと出力経路に必要な決定 | フロントエンドの意味解析 |
| Artifact | 外部ツールまたは実行環境が利用する出力 | コンパイラの可変内部状態 |

この分離により、構造化された意味を保ったまま、「構造が制御フローへ変わる過程」自体を観測対象にできます。Control-flow IRへ直ちにSSAを要求しません。値の合流方法は、実際の制御構文を設計するときに決めます。

### 出自を位置情報から分離する

将来の出自モデルは、概念上、次の情報を区別します。

```text
Entity
  - compilation-local identity
  - stage
  - kind
  - origin

Origin
  - Source(source identity, span)
  - Derived(input entities, pass)
  - Synthetic(pass, reason)
```

これはRust APIや公開スキーマを確定する定義ではありません。必要な意味を整理するための概念モデルです。

- `Source`はソース位置に直接対応する要素を表します。
- `Derived`は一つ以上の前段要素から変換された要素を表します。
- `Synthetic`は前段に直接対応する要素を持たず、passやloweringが理由を持って生成した要素を表します。
- 要素の識別子は操作権限ではなく、コンパイル結果内の関係を参照するためだけに使います。

現在のbytecodeの`Source(span)`と`Synthetic`は、この方向へ進む最初の実装として維持できます。用途が生じる前に、すべての内部表現を一度に汎用化する必要はありません。

要素の消去は、後段の要素に出自を付けるだけでは表せません。必要になった時点で、pass前後のスナップショットを比較するか、変換記録として表す方法を検討します。

### 成果物との対応を副次データとして保持する

emitterは、出力したテキストまたは命令の範囲と、対応する内部要素を副次的な対応表へ記録できます。

```text
Emission Map
  artifact range -> backend entity
  backend entity -> origin chain
```

対応表は成果物へ埋め込まず、成果物の内容を変えない読み取り専用データとして扱います。これにより、観測機能の有効または無効によって生成結果が変わることを防ぎます。

### 観測結果を不変なスナップショットとして扱う

観測側へコンパイラ内部の可変状態を渡しません。必要な段階の情報を、内部状態から切り離した不変なスナップショットとして提供します。

スナップショットは、次の性質を持ちます。

- 読み取り専用である
- コンパイル処理へ情報を戻さない
- 同じ明示的な条件から決定的に生成される
- 観測しない場合と同じ成果物を生成する
- 内部の所有権やメモリアドレスを公開しない

内部スナップショットを保持することと、それを公開互換APIにすることは別の判断です。

## セキュリティと再現性

- ソース本文とファイルパスは、利用者が明示的に要求した場合にのみ公開します。
- secret値は、広い観測が要求された場合でも実際の値を公開しません。
- ソース位置だけで十分な診断では、本文やパスを暗黙に付加しません。
- 観測識別子から、ファイル操作、pass実行、コンパイラ状態の変更を行えるようにしません。
- 外部プラグインや書き換えフックは、観測APIとは別の機能と権限として設計します。
- タイムスタンプ、メモリアドレス、ランダム値、HashMapの偶発的な順序を観測結果へ含めません。
- 大きなプログラムや悪意のある入力に備え、観測結果へサイズと要素数の上限を設けます。
- 診断や観測テキストでは、制御文字を安全に扱います。

## 合意した構文の方向

ここでは、現在の仕様として実装済みの構文と、将来の実装に対する設計方向を区別して記録します。未実装の項目は言語リファレンス上の機能ではありません。

### 宣言、可変性、参照

- 新しい束縛は`name: type_spec = expression;`と書き、`let`や`var`を宣言の印として追加しません。
- `type_spec`には具体型または`infer`を必ず書きます。
- 束縛は標準で不変とし、再代入できる束縛だけ`mut name: type_spec = expression;`と書きます。
- `mut`は型ではなく、名前の再代入を許可する指定です。
- 将来の`ref T`は読み取り専用の参照とし、参照を通した書き換えは最初の参照設計へ含めません。

`mut`と再代入は現在の仕様として実装済みです。`ref`は設計方向だけが決まっており、未実装です。

### 関数とentry point

- 名前付き関数は`fn`で明示します。
- parameterと戻り値の型は具体型で明示し、戻り値がない関数は`void`を指定します。
- 値を返す関数では`return expression;`を明示し、block末尾の式を暗黙の戻り値にしません。
- `void`関数はblock末尾で終了でき、`return;`で途中終了できます。
- `main`を省略したプログラムでは、トップレベル実行文からcompiler生成のentry pointを作ります。
- 明示的な`fn main`がある場合、トップレベル実行文と同時には使用できません。
- command-line argumentは、生の`argc`と`argv`ではなく、runtimeが提供する読み取り専用の`Args`で受け取ります。
- targetが要求されたargument機能に対応しない場合、空の値へ暗黙に置き換えず診断します。

関数、`void`、明示的な`main`は実装済みです。現在の関数シグネチャはscalar型と最大4個のparameterに限定し、再帰はすべてのbackendで安全に扱えるまで診断します。`Args`は未実装です。詳細は[関数の設計](functions.ja.md)に記録します。

### 構造化された制御

- `if condition { ... } else { ... }`は文として実装済みです。`else`は省略できます。
- `while condition { ... }`は文として実装済みです。条件は本文の実行前に毎回評価します。
- `for (start; condition; update) { ... }`は文として実装済みです。開始文には束縛または再代入を書けます。開始文、継続条件、本文、更新文はPrimer IRで区別して保持します。
- `break;`と`continue;`は実装済みで、最も内側のloopだけを対象にします。
- blockはlexical scopeを作り、内側の束縛は外側から見えません。内側から外側の`mut`へは再代入できます。
- ソース言語へ`goto`、任意位置のlabel、computed gotoを導入しません。
- `foreach`、`switch` / `case` / `default`を将来の基本制御構文とします。
- `foreach`が導入する名前にも`: type_spec`を要求します。
- `switch`のcase間に暗黙のfallthroughを認めず、case終了用の`break;`を要求しません。
- backend内部のbranchとjumpは許可しますが、元となった構造化制御との対応を保持します。

`foreach`と`switch`は未実装です。`if`を将来、値を作る式としても追加するかは引き続き検討します。

## Issue #2で決めること

[Issue #2](https://github.com/Hokutaka/Primer/issues/2)では、実装へ入る前に次の順で判断します。

### 1. IR段階

- Structured Primer IRを現在の主要な意味表現として維持するか
- Control-flow IRを独立した段階として導入するか
- 各段階の不変条件は何か
- どの段階を公開観測面にするか

推奨案は、Structured Primer IRを維持し、Control-flow IRを別段階として導入することです。公開観測面の追加は、内部表現と用途が安定するまで保留します。

### 2. 関数とエントリーポイント

- 現在のトップレベル文を維持するか
- 暗黙のエントリーポイントへloweringするか
- 明示的な`main`を要求するか
- parameter、return type、local scopeをどう表すか
- 再帰とforward referenceをいつ許可するか

### 3. 制御構文

- `if`を文とするか、値を返す式とするか
- 条件に使用する型をどう定義するか
- early returnと到達不能なblockをどう扱うか
- 値の合流にblock parameter、phi、別の表現のどれを使うか
- loop、`break`、`continue`の関係をどう表すか

### 4. ユーザー定義型と複合型

ユーザー定義型は、Primerを汎用言語にするための必要条件とします。複数の値をまとめる複合型（aggregate type）は、名前付きproduct typeと固定長配列として最初の具体化を実装しました。

名前付きproduct typeは[名前付きproduct typeの設計](product-types.ja.md)、固定長配列は[固定長配列の設計](fixed-arrays.ja.md)に分離して整理します。

次を設計します。

- 名前付き型を、名前によって区別するnominalな型にするか、構造だけで区別するか
- 既存の型へ別名を付けるtype aliasと、新しい型を作る定義をどう区別するか
- tuple、sum type（複数の形のいずれかを持つ型）をどの順序で導入するか
- 値の作成とfield accessをどう表すか
- aggregateを値として扱う範囲
- 不変性、更新、copy、move、borrowなどの意味をどこまで導入するか
- generic typeと型引数をいつ導入するか
- memory layoutをどの段階で決定するか
- ABIとの境界をどこに置くか

名前付きproduct typeはnominalな型として、固定長配列は要素型と長さで区別する型として実装しました。どちらも値としてコピーし、内部の一部を直接書き換えません。tuple、sum type、generic type、再帰型、参照、custom layoutは、同じ型システム上で必要性と依存関係を整理します。

Primer IRでは型名、field、型引数などの意味を保持し、サイズ、配置、アラインメント、calling conventionは原則としてbackend lowering以降で決定します。型がfield、メモリ、レジスタ、命令へ分解される過程と、型の抽象化が失われる地点を出自と変換記録で追跡します。

ユーザーが型を定義できることと、外部コードが型検査器やコンパイラ内部を直接変更できることは区別します。ユーザー定義型はPrimerプログラムの入力であり、観測と制御の境界を越える拡張権限ではありません。

### 5. バックエンド対応方針

次のどちらを採用するか決めます。

| 方針 | 利点 | 課題 |
| --- | --- | --- |
| すべての出力経路を同時に対応 | 言語仕様と全出力経路が常に一致する | 一つの機能追加が大きくなる |
| 対応状況を明示して段階導入 | 意味とIRを小さく検証できる | capability表示と未対応診断が必要 |

段階導入を採用する場合も、未対応の経路がpanic、不正な成果物、暗黙のfallbackを起こすことは認めません。対応状況を機械的かつ決定的に確認できる必要があります。
